BMAD-via-MCP platform

A proof-of-concept platform that lets product managers, architects and UX roles run BMAD's spec-driven workflows with enterprise, workflow and project context, and publish the results to Jira.

Status
Proof of concept
My role
Primary builder, with one teammate on the frontend
Tech stack
Python · React (Vite) · MCP · Gemini, with other LLMs via an API key
Works with
BMAD · Jira · Microsoft Teams

How a workflow runs

  1. Pick a project and a workflow out of the six.
  2. Add context. Enterprise context is already in place. Add project context and a workflow manifest.
  3. Work with the LLM in a conversation and refine the artifact.
  4. Publish to Jira. The artifact goes up with its decision trace.
  5. Get approval in Jira, then move on to the next workflow.

The last workflow publishes all epics and their child user stories to Jira.

Overview

BMAD is a spec-driven development method that developers normally use inside an IDE. This platform wraps BMAD's MCP server in a web application, so product managers, architects and UX roles can run its workflows themselves. Each workflow produces an artifact, and the platform keeps the decisions that led to it.

Problem and context

The idea was to apply context engineering and spec-driven development with AI. Context engineering means giving the model the right project context. Spec-driven development means agreeing a clear specification before building.

BMAD supports this, but it is built for developers working in an IDE. Product managers and architects mostly work in tools such as Jira and Confluence, not in an IDE. Using this approach with those roles was also requested by stakeholders, so we built an application around BMAD for them.

My role and contribution

I built most of the platform. A teammate built the frontend, and I later refined it after talking to the UI/UX team.

An account-level technology lead shared ideas and checked progress, and a senior technical colleague guided when I asked for input.

What the platform does

It offers six workflows, one for each stage of early product definition:

  • Brainstorming
  • Product Brief
  • PRD
  • Architecture
  • UX Design
  • Epics and Stories

Three kinds of context shape every workflow:

Enterprise context

Uploaded once at enterprise level. It holds organization context, engineering standards, architectural standards and similar material.

Workflow customization

For each workflow, at project level, the user adds a manifest file in TOML. It can hold persistent facts, an artifact template and a definition of done.

Project context

Optional, added before starting. It can be typed in, uploaded as a Markdown file, or pulled in by naming a Jira story.

The platform connects to the tools teams already use:

Jira

Connected with a personal access token (PAT). It could also connect through MCP. Jira holds each artifact for approval and, at the end, all epics and their child user stories.

Microsoft Teams

Receives notifications for workflows, publications and approvals.

Architecture and implementation

The backend is written in Python and the frontend is built with Vite and React. A custom MCP client connects the application to BMAD's MCP server.

For each workflow, the application composes a prompt: BMAD's base workflow prompt, plus enterprise context, workflow customization and the project's own context. The result goes to an LLM. An orchestrator keeps track of workflow state and prerequisites, and artifact versions and lineage are stored.

Gemini is the default model. Other models such as Claude or OpenAI can be used by adding an API key.

  • Python
  • React (Vite)
  • MCP
  • GmGemini

Approvals and decision trace

The platform stores a decision trace: the decisions the person gave the LLM to arrive at an artifact. The artifact and its decision trace are published to Jira as an attachment on an epic or story, and the artifact must be approved there before the user can move on.

Approvals started inside the application. It has personas, so a product manager creating an architecture could send it to an architect for approval. I later moved approvals to Jira. This is configurable per workflow, and we kept it for the PRD workflow.

Why Jira

We did not want people to stop using Jira, or to compete with it. Product managers already work across several platforms and have to prioritize their tools, and most teams track stories in Jira or a similar tool, so the platform avoids adding more complexity. Attaching artifacts to epics and stories also makes them easy to find in later stages.

Outcome, feedback and next steps

The proof of concept was delivered with six workflows, Jira and Teams integration, and a configurable approval flow.

After a demo, the CTO and senior teams gave positive feedback. It suggested taking the platform further, from epics and stories into implementation and deployment.

Implementation and deployment

Extend the workflows beyond epics and stories.

Brownfield applications

The proof of concept focused on greenfield (new) applications. The next step is to cover existing ones.

Institutional memory

A knowledge graph of approved, well-written project learnings, so people across the organization can reuse them instead of starting from scratch.
